# API Testing: Complete PortSwigger Web Security Academy Guide

Reference: https://portswigger.net/web-security/api-testing

## Room Overview & Information

**Category:** Web application security  
**Format:** Practical methodology and lab notes  
**Topics:** API discovery, endpoint enumeration, HTTP request analysis, authentication, object-level authorization, mass assignment, input validation, rate limiting, and API-specific remediation.

This is a PortSwigger topic guide rather than a single boot-to-root machine. The target URLs, accounts, endpoints, and request bodies depend on the active Academy lab. Use the supplied lab instance only and copy machine-specific values from the browser or request history rather than inventing them.

## Phase 1: Reconnaissance & Enumeration

### 1. Map the API surface

Begin by using the web application's normal features and recording the requests in the browser Network panel or Burp Suite HTTP history. Build an inventory with HTTP method, path, purpose, authentication context, user-controlled fields, and expected permissions.

Useful evidence sources include:
- Browser network requests generated by each page or form.
- OpenAPI, Swagger, or other API documentation intentionally exposed by the lab.
- JavaScript bundles and API client code delivered to the browser.
- Error messages that reveal route, parameter, or schema information.
- Versioning patterns such as /api/v1/ and /api/v2/.

An undocumented route is not necessarily vulnerable. The goal is to understand which component handles each request and which controls should protect it.

### 2. Capture a baseline request

Use an ordinary test account to make one legitimate request. In Burp Suite, send the request to Repeater and preserve an unchanged copy. Record the method, path, headers, cookie or authorization context, content type, and body.

A command-line baseline can be useful when the lab exposes a simple endpoint:

~~~bash
curl -i -H 'Accept: application/json' 'https://LAB_HOST/api/status'
~~~

- **curl** sends the HTTP request.
- **-i** includes response headers in the output.
- **-H** adds the Accept header, requesting a JSON representation.
- The URL must be replaced with the endpoint from the active lab.

Do not include live session tokens in public screenshots or repository notes.

### 3. Inspect the response

Record the status code, Content-Type, response body, and relevant headers. A 200 response proves only that the server returned a successful HTTP status. It does not demonstrate that authorization, validation, or business logic is secure.

For JSON responses, identify which fields are returned and whether they contain data that the current user should not receive. For error responses, determine whether the error leaks internal paths, stack traces, secrets, or database details.

## Phase 2: Vulnerability Analysis & Controlled Validation

### 4. Authentication and authorization

Authentication identifies the caller. Authorization decides which operation that caller may perform. An API can authenticate a user correctly and still have broken access control.

Test authorization with the user accounts and objects provided by the lab:
1. Capture a request that succeeds for account A.
2. Identify the object identifier or privileged operation.
3. Repeat the request under account B, changing only the relevant object or permission context.
4. Compare the body and resulting application state.
5. Confirm whether account B obtained data or performed an action that policy should forbid.

Horizontal access-control failure occurs when one user accesses another user's resource at the same privilege level. Vertical failure occurs when a lower-privileged user invokes a function reserved for a higher role. The server must check permissions on every request, including direct API calls that the UI hides.

### 5. Object-level authorization and identifier tampering

Look for API paths that include an object identifier, such as /api/orders/104 or a JSON field that selects an account. Predictable identifiers make testing easy, but random identifiers do not replace authorization.

Use only the lab's test records. A changed identifier returning HTTP 200 is not sufficient evidence: inspect whether the response contains another user's protected data or whether the intended state change occurred.

### 6. Mass assignment and excessive data exposure

Mass assignment occurs when the server binds client-supplied fields to an internal object without explicitly limiting writable properties. A response may include fields such as role, owner, price, or approval status that ordinary users should not control.

Compare the documented schema, ordinary request body, and returned object. Test only fields that the lab instructs you to investigate. Verify any state change rather than assuming that a field accepted by the parser was persisted.

Excessive data exposure is the inverse kind of problem: the API returns more information than the caller needs, leaving the client to hide it. Sensitive fields should be omitted by the server for users who are not authorized to see them.

### 7. Input validation and API semantics

Check how the API handles:
- Missing required fields.
- Unexpected data types, such as a string where an integer is expected.
- Extra JSON properties.
- Empty or extremely large values.
- Unsupported HTTP methods.
- Invalid state transitions or repeated requests.
- Content-Type mismatches.

Change one field at a time and preserve the baseline. Use harmless values and avoid destructive requests. A 400 or 500 response may indicate input validation or an application error, but it does not prove that injection or another vulnerability exists.

### 8. Rate limiting and workflow abuse

API endpoints can be abused through repeated login attempts, resource-intensive queries, or repeated business actions. Observe rate-limit headers, throttling behaviour, and how the application responds to reasonable request volume in the lab. Do not stress-test services or create large request floods unless the lab explicitly provides a bounded test.

For workflow vulnerabilities, define the business invariant first. For example, a transaction must not be approved twice, and a user must not change another account's recovery address. Test whether the server enforces the invariant even when requests are replayed or sent out of order.

## Phase 3: Exploitation Impact & Post-Test Validation

A valid finding should explain the precondition, the minimal request change, the observed effect, and the security impact. Keep evidence sanitized. Avoid collecting unrelated user data, dumping entire databases, or modifying records outside the challenge objective.

If a request fails in Burp Repeater but works in the browser, compare cookies, authorization headers, CSRF tokens, Origin, Content-Type, and request body. A 401 commonly indicates missing or invalid authentication; 403 commonly indicates insufficient permission. Applications vary, so inspect the response instead of relying solely on status-code conventions.

Use a controlled retest after applying a fix. Confirm both that the previously unauthorized request is rejected and that the legitimate user workflow still succeeds.

## Phase 4: Lab Questions & Evidence Walkthrough

For each PortSwigger lab:
1. Read the lab objective and identify the security property being tested.
2. Capture the normal request and identify the exact parameter or field.
3. Form one hypothesis about the control that may be missing.
4. Change only the relevant request element in Repeater.
5. Observe the response and verify the actual impact.
6. Record the request, status, sanitized output, and conclusion.
7. Submit the lab only after the target confirms completion.

This repository guide covers the method across API labs; it does not invent one universal endpoint, flag, or response. Use the active lab's own URL and result as the source of truth.

## Phase 5: Key Takeaways & Remediation

- Enforce object-level and function-level authorization on every request.
- Use explicit request schemas and allowlist writable properties.
- Return only the fields that the caller is authorized to receive.
- Validate data server-side and use parameterized queries or safe APIs for downstream interpreters.
- Apply quotas, rate limits, request-size limits, and timeouts.
- Authenticate administrative routes and remove debug endpoints from production.
- Log sensitive actions with enough context for investigation while redacting credentials and tokens.
- Maintain an API inventory, document intended permissions, and test denied as well as allowed cases.

The essential API-testing workflow is baseline, one controlled modification, verified impact, and a fix at the server-side trust boundary. Tools help make the experiment repeatable; they do not replace the evidence needed to prove the finding.
