# Phantom Fob: TryHackMe Walkthrough

Room: https://tryhackme.com/room/phantomfob

The fob can lock the demo car and sound its horn, but it has no unlock button. The room gives access to a simulated vehicle CAN bus and asks me to understand the messages well enough to construct the missing unlock command. The codes change every second, so replaying an old frame is not the intended solution.

## 1. Start the simulation

Start the lab machine and follow the room's instructions for connecting to the simulated CAN interface. Keep the exercise inside the provided environment; do not connect experiments to a real vehicle. Record the interface name and any tool commands supplied by the room.

## 2. Understand the CAN frame

A CAN frame contains an identifier and a data field. The identifier helps describe the message's purpose or priority, while the data bytes carry the payload. The exact meaning depends on the vehicle's message definitions and the device that consumes the frame.

The vehicle's control units broadcast messages on a shared bus. Locking a door, sounding the horn, and other actions may produce frames with different identifiers or data. Observing these differences is the first step toward understanding the protocol.

## 3. Capture known actions first

Use the lab's provided interface and instructions to capture the traffic generated by the known Lock and Horn buttons. If the environment uses a tool such as candump, follow the exact interface syntax given in the task.

For each action, record:
- The CAN identifier.
- The data bytes.
- The timestamp.
- Whether the action succeeded.
- Any fields that change between repeated presses.

Repeat the known action if the room permits it. Comparing several samples can reveal which bytes represent the action and which may be time-dependent. Do not assume a single observed frame is a complete message format.

## 4. Understand changing codes

The room explicitly notes that codes change every second. This means a captured frame may be stale by the time it is replayed. A secure rolling-code design typically includes a changing value and checks it against the receiver's expected state, reducing the usefulness of replaying an old message.

The task is to infer the format and timing from the simulated traffic, not to blindly resend an old frame. Follow the room's hints about how the data changes and test one hypothesis at a time.

## 5. Construct and validate the unlock command

Once the message structure is understood, follow the room's instructions to build the Unlock message in the simulation. Verify that the car responds to the command and preserve the frame evidence that supports the conclusion.

If the command fails, check the identifier, byte ordering, payload length, and time-dependent fields against the observed examples. A failed replay does not necessarily mean the frame format is wrong; the changing code may have expired.

## 6. Security lessons

A vehicle network should not trust an unauthenticated command merely because it has a plausible identifier and payload. Strong message authentication, replay protection, key management, and security testing reduce the risk of forged control messages. CAN itself does not provide modern cryptographic authentication by default, so vehicle architecture must add protections where needed.

## Phase 2: Compare frames, not just individual bytes

CAN frames include an identifier and a data payload. The identifier helps recipients determine which message a frame belongs to, while the payload is interpreted according to the vehicle's own message format. A single identifier may be repeated with changing bytes.

Capture more than one sample of the same action. Compare which fields remain constant and which vary over time. Avoid assuming the entire payload represents a fixed command; it may include a counter, rolling code, state value, or checksum.

## Phase 3: Understand the anti-replay behaviour

The room notes that codes change every second. That makes simple replay of an old frame unreliable. A rolling-code system generally validates changing state at the receiver; a captured value may expire or be rejected if it is out of sequence.

The task is to understand the simulated protocol from the observed examples and the room hints, not to replay frames against a real car. Keep tests in the virtual environment.
